# Score victims inside ARC, learn live

The plan is to stop training the eviction model with reinforcement learning. Instead, run **supervised imitation of Belady's MIN, updated online from delayed "when was this key requested next?" labels, inside an ARC shell**. In that shell, ARC's own REPLACE rule picks which list (T1 or T2) gives up a slot. A small calibrated model then picks the victim among the four coldest entries of that list, and when the model abstains or falls behind, the cache is exactly ARC. This keeps the literature's winning recipe: Parrot, LRB, HALP and 3L-Cache all learn from future-derived labels, and Parrot's authors found that an RL formulation "results in lower performance" than imitation ([Liu et al., ICML 2020](https://arxiv.org/abs/2006.16239)). It also fixes a ceiling problem that a smoke test run for this plan exposed on the project's own traces. Even a *perfect* scorer choosing among 4 LRU-tail candidates (the current architecture's shape, and HALP's candidate count) **loses to plain ARC in 3 of 4 trace/size settings**, while the same perfect scorer inside ARC's chosen list **beats LRU, SIEVE, S3-FIFO and ARC in all 4**. ARC therefore earns four roles: mandatory baseline, data-plane shell and candidate generator, key-only shadow and fallback in place of LRU, and a cheap drift signal through swings in its target p. No published paper builds a learned or RL-controlled ARC, so the shell design is our inference plus a local oracle measurement. It must survive a Phase 0 check on real traces, where S3-FIFO usually beats ARC ([S3-FIFO, SOSP 2023](https://dl.acm.org/doi/10.1145/3600006.3613147)). The user-suggested techniques keep narrow places. RLCR's calibration result becomes a Brier or log-loss head, not an RL loop. ModernBERT and mmBERT stay off the hot path, because the keys are opaque integers and those encoders cost milliseconds against a microsecond budget. Learning ARC's p at the policy level (the LeCaR/CACHEUS/LAH lineage) is a credible lighter alternative, kept as a stretch option because its only strong evidence comes from a preprint that tuned S3-FIFO, not ARC.

## The current agent learns LRU's shadow, not eviction

The present design fails for structural reasons, not tuning ones. The training loop in `rl_tail.py` stores the *requested* item's features, gives +1 for a hit and −1 for a miss, and always evicts with `popitem(last=False)`, which is plain LRU. The value network is therefore never shown a candidate set, never takes an action, and never sees the consequence of its own evictions. Because `next_state` is always the just-inserted item (recency 0, rank near the end), the bootstrapped term γ·V(s′) is close to a constant. The network ends up regressing something like "would a request with these features have hit under LRU?", which is a model of LRU's own membership rule and not a model of which resident key is safest to drop. At inference, `RLHybridCache` then applies this state-value function as an argmin over 16 LRU-tail candidates. That is a use it was never trained for, on a feature distribution it never saw: the training features describe items at the moment they are requested, while the inference features describe resident items that are *not* being requested. The frequency feature is a raw all-time count in a dict that is never aged or pruned, so it grows without bound and never forgets stale popularity. LRB's multi-horizon decayed counters, by contrast, are designed to forget ([LRB §4.3.1](https://www.usenix.org/system/files/nsdi20-paper-song.pdf)).

The literature names each of these flaws and supplies the fix. Parrot shows that imitation must be trained on the states the learned policy itself visits (DAgger), and that doing so adds **9.8% normalized hit rate** over off-policy training ([Parrot §5.3](https://arxiv.org/abs/2006.16239)). The current agent is trained entirely off-policy, and on LRU's trajectory at that. In a trace-driven simulator the future request stream does not depend on the eviction decision. The true next-use time of every candidate, including evicted ones, is therefore observable after a delay, which makes eviction a full-information supervised problem. The RL machinery (TD bootstrapping, a target network, a replay buffer) solves a harder problem the project does not have ([Chledowski et al., ICML 2021](https://arxiv.org/abs/2106.14693); [Parrot](https://arxiv.org/abs/2006.16239)). There is an irony in the repository: `data/zipf_100k.csv`, `data/web_traffic_100k.csv` and `data/training_data.csv` already carry a `time_to_next_request` column, which is exactly the Belady label, and the trainer ignores it.

The evaluation is equally thin. The agent trains once on about 18k synthetic Zipf requests, never updates online, has no confidence estimate or fallback, and is compared only against LRU. A capacity of 30 against the 18,486 distinct keys in `zipf_100k.csv` is about **0.16% of the footprint**. That is close to the 0.1% "small cache" setting of recent evaluations, so cache size is not the problem. The problem is a single synthetic trace at a single size, with LRU as the only opponent. Credible work reports results over hundreds to thousands of real traces, at two or more cache sizes, against S3-FIFO, SIEVE, ARC, TinyLFU, LHD/GDSF and learned baselines ([3L-Cache §5.1](https://www.usenix.org/system/files/fast25-zhou-wenbin.pdf)). A learned policy that only beats LRU is not a result. On speed, the per-candidate Python loop that builds the state matrix, plus three small `np.dot` calls, is almost certainly dominated by interpreter dispatch rather than arithmetic. That is reasoning, not a measurement, so the team should confirm it with `InstrumentedRLHybridCache` before rewriting anything.

## Future-labelled supervision beats reward-driven RL at every scale

Over a decade, one recipe has converged: **label from the future, train a cheap supervised model, and score only a small candidate set from the cold end of a queue.** Hawkeye reconstructs Belady's decisions on past accesses to produce binary cache-friendly/averse labels ([Mockingjay paper's description](https://www.cs.utexas.edu/~lin/papers/hpca22.pdf)). Mockingjay replaces the binary label with multiclass reuse-distance prediction and evicts the line with the farthest estimated arrival, reaching **+5.7% over LRU single-core versus Belady's own +6.0%** ([Shah et al., HPCA 2022](https://www.cs.utexas.edu/~lin/papers/hpca22.pdf)). Parrot imitates Belady with an LSTM and attention, trained with DAgger, and reports a **61% normalized hit-rate improvement over LRU on Google Web Search** ([Liu et al., ICML 2020](https://arxiv.org/abs/2006.16239)). LRB regresses log(time to next request) with LightGBM on up to 32 inter-arrival deltas and 10 exponentially decayed counters. It samples 64 candidates, cuts CDN WAN traffic by **4–25% versus B-LRU** across six production traces, and beats both a UCB bandit and LeCaR ([Song et al., NSDI 2020](https://www.usenix.org/system/files/nsdi20-paper-song.pdf)).

Two production-minded refinements matter most for this project. HALP has almost the same architecture as the current code: a heuristic proposes 4 candidates and a one-hidden-layer MLP picks among them. HALP, however, is trained fully online on **pairwise "which of these two was re-accessed first" labels**, resolved asynchronously through a ghost cache. Its authors note that the candidate heuristic "can be selected as LRU, LFU, or other heuristic policies", though they found LRU sufficient for YouTube. It has run as YouTube's DRAM eviction policy since early 2022 ([HALP PDF](https://www.usenix.org/system/files/nsdi23-song-zhenyu.pdf); [Google Research blog](https://research.google/blog/preference-learning-with-automated-feedback-for-cache-eviction/)), cutting **peak byte miss by an average of 9.1% at 1.8% CPU overhead** ([HALP, NSDI 2023](https://www.usenix.org/conference/nsdi23/presentation/song-zhenyu)). 3L-Cache pares the approach down to **6 features** (age, size, window frequency and the last 3 inter-arrival times) with a LightGBM regressor retrained every 32K–64K labels. It wins byte miss ratio on 69.8% of 4,855 traces at small cache sizes, at **60.9% less CPU than HALP and 94.9% less than LRB** ([Zhou et al., FAST 2025](https://www.usenix.org/system/files/fast25-zhou-wenbin.pdf)).

The same 3L-Cache study supplies the sobering numbers. Measured as mean miss-ratio reduction versus LRU across thousands of traces, LRB, HALP, LeCaR and CACHEUS land in the **low single digits**. S3-FIFO, a three-FIFO heuristic, placed third in byte miss ratio and **beat HALP**. GL-Cache had a worse byte miss ratio than LRU on large caches ([3L-Cache Table 1, §5.2](https://www.usenix.org/system/files/fast25-zhou-wenbin.pdf)). S3-FIFO itself reports up to **72% lower miss ratio than LRU** over 6,594 traces, at 6× the throughput of optimized LRU at 16 threads ([s3fifo.com](https://s3fifo.com/)). SIEVE is best of 10 algorithms on over 45% of 1,559 traces and needs fewer than 20 changed lines to adopt ([Zhang et al., NSDI 2024](https://www.usenix.org/conference/nsdi24/presentation/zhang-yazhuo)). The newest direction goes further. Learning-Augmented Heuristics (LAH) learns only the *parameters* of S3-FIFO from cache-level features. It reports +26% mean efficiency over S3-FIFO and +8% over 3L-Cache, with a worst-case regression versus FIFO of **0.8% against 3L-Cache's 8.8%** and LRB's 20–72%. That work is an August 2026 arXiv preprint whose OSDI '26 listing was not independently confirmed ([Xia et al., arXiv:2608.27975](https://arxiv.org/abs/2608.27975)).

Pure RL has a weaker record. The strongest RL-derived CPU policy, RLR, used a DRL agent only offline as a design tool and hand-distilled it into a rule that gains +3.25% single-core, less than Mockingjay ([Sethumurugan et al., HPCA 2021](https://experts.umn.edu/en/publications/designing-a-cost-effective-cache-replacement-policy-using-machine/)). Cold-RL (2025) mirrors the current project closely: a dueling DQN over the K least-recently-used objects, served through ONNX with an LRU fallback. It is an unreviewed preprint whose workloads look synthetic. Its reported ARC hit ratios almost equal its LRU ones (0.144 at 25 MB), which makes the ARC comparison weak evidence ([Gupta & Bhayani, arXiv:2508.12485](https://arxiv.org/html/2508.12485v1)). Its one lesson worth keeping is the per-candidate reward: "was the *retained* object hit before a horizon?" That credits the specific decision, which the current reward does not, and it amounts to a delayed binary Belady label.

## ARC is four LRU lists and one self-tuning scalar

ARC (Megiddo and Modha, IBM, FAST 2003) is the canonical **policy-level adaptive heuristic**. It never ranks individual objects. It learns one number, the target size p of its recency region, and makes every other decision by plain LRU ([ARC FAST'03](https://www.usenix.org/legacy/events/fast03/tech/full_papers/megiddo/megiddo.pdf)). That makes it the natural reading of the user's phrase "policy type base": a base policy whose intelligence lives in how it splits capacity, not in per-object scores. The paper's model is demand paging with uniformly sized items, which matches this project's simulator exactly, so the original algorithm applies unmodified.

### How ARC decides, in one screen

ARC keeps four LRU-ordered lists. **T1** holds resident keys seen once recently, and **T2** holds resident keys seen at least twice. **B1** and **B2** are *ghost* lists: they hold only the keys (no data) of items recently evicted from T1 and T2 respectively. The invariants are |T1| + |T2| ≤ c, |T1| + |B1| ≤ c and |T1| + |T2| + |B1| + |B2| ≤ 2c. The directory therefore remembers exactly twice the cache size, and every request costs **O(1)** ([ARC FAST'03](https://www.usenix.org/legacy/events/fast03/tech/full_papers/megiddo/megiddo.pdf)). The adaptive part is the target p ∈ [0, c], the desired size of T1. A hit in B1 means "I evicted a recency item too early", so p grows by max(1, |B2|/|B1|). A hit in B2 means "I evicted a frequency item too early", so p shrinks by max(1, |B1|/|B2|). The ratio makes the step larger when the ghost list being hit is the smaller one, which the paper calls a learning rate. **REPLACE** evicts the LRU end of T1 into B1 when T1 is non-empty and either |T1| > p, or |T1| = p and the incoming key came from B2. Otherwise it evicts the LRU end of T2 into B2. Fix p and drop the adaptation steps, and ARC becomes the fixed-split policy FRC_p ([ARC FAST'03](https://www.usenix.org/legacy/events/fast03/tech/full_papers/megiddo/megiddo.pdf); [libCacheSim ARC.c](https://github.com/1a1a11a/libCacheSim/blob/develop/libCacheSim/cache/eviction/ARC.c)).

The implementation below follows the paper's prose, cross-checked against libCacheSim's ARC.c. libCacheSim itself says it was cross-checked against a small Python ARC and uses a float p, because the paper leaves int versus float open. The research notes tested this class against all four invariants over 200k mixed Zipf-plus-scan requests. This plan re-ran it over `zipf_100k.csv` at c = 30 and c = 300 with invariant assertions on every request, and every assertion held. libCacheSim adds a `|T2| == 0` guard to REPLACE for its variable-size mode; with uniform sizes the paper's version below is sufficient.

```python
from collections import OrderedDict as OD
class ARC:  # FAST'03 Fig. 4, uniform sizes; OrderedDict first = LRU end, last = MRU end
    def __init__(s, c): s.c, s.p = c, 0.0; s.T1, s.T2, s.B1, s.B2 = OD(), OD(), OD(), OD()
    def _replace(s, x_in_B2):
        if s.T1 and (len(s.T1) > s.p or (x_in_B2 and len(s.T1) == s.p)):
            k, _ = s.T1.popitem(last=False); s.B1[k] = None
        else:
            k, _ = s.T2.popitem(last=False); s.B2[k] = None
    def access(s, x):  # returns True on hit
        if x in s.T1: del s.T1[x]; s.T2[x] = None; return True
        if x in s.T2: s.T2.move_to_end(x); return True
        if x in s.B1:
            s.p = min(s.c, s.p + max(1, len(s.B2) / len(s.B1)))
            s._replace(False); del s.B1[x]; s.T2[x] = None; return False
        if x in s.B2:
            s.p = max(0, s.p - max(1, len(s.B1) / len(s.B2)))
            s._replace(True); del s.B2[x]; s.T2[x] = None; return False
        L1 = len(s.T1) + len(s.B1)
        if L1 == s.c:
            if len(s.T1) < s.c: s.B1.popitem(last=False); s._replace(False)
            else: s.T1.popitem(last=False)
        else:
            tot = L1 + len(s.T2) + len(s.B2)
            if tot >= s.c:
                if tot == 2 * s.c: s.B2.popitem(last=False)
                s._replace(False)
        s.T1[x] = None; return False
```

ARC's descendants map its design space. **CAR/CART** (FAST 2004) keep ARC's adaptive target but replace the LRU lists with CLOCKs, so hits no longer serialize behind a global lock. CART also adds a short/long-term filter bit per page, because "two consecutive hits" is not "a guarantee of long-term utility" ([Bansal & Modha, FAST 2004](https://www.usenix.org/legacy/publications/library/proceedings/fast04/tech/full_papers/bansal/bansal.pdf)). A learned reuse probability generalizes that bit. **OpenZFS** began from ARC. Its 2.2 release removed the scalar `arc_p` in favour of rate-limited, fraction-based balancing driven by ghost-hit *bytes*, and it caps ghost lists because "excessive ghost size may result in false ghost hits (too far back)" ([OpenZFS arc.c](https://github.com/openzfs/zfs/blob/master/module/zfs/arc.c); [PR #14359](https://github.com/openzfs/zfs/pull/14359)). That is a practitioner's admission that the raw p rule misjudges its step size. **2Q** is essentially ARC with a static 25% recency region ([SIEVE, NSDI 2024](https://www.usenix.org/system/files/nsdi24-zhang-yazhuo.pdf)). IBM's core patent US6996676 is listed as **expired since February 2024** ([Google Patents](https://patents.google.com/patent/US6996676B2/en)). A search snippet suggests the related US7469320 runs to February 2027 ([Google Patents](https://patents.google.com/patent/US7469320B2/en)); that is unverified, and irrelevant for a research simulator.

### Five ways ARC fails, all of them documented

ARC's adaptation finds the right *direction* but often the wrong *size*. On Twitter traces it shrinks the recency region to **about 0.01% of the cache**. Newly popular objects keep missing before they can reach T2, and objects evicted from T2 return soon after ([S3-FIFO](https://dl.acm.org/doi/10.1145/3600006.3613147)). SIEVE's authors see the same collapse at small cache sizes and note that ARC "has no explicit parameters" yet uses "implicit parameters in deciding when and how much space to move" ([SIEVE](https://www.usenix.org/system/files/nsdi24-zhang-yazhuo.pdf)). The step size is arbitrary ("why one slot instead of half or two?"), small perturbations make it overreact, and gradient-style adaptation implicitly assumes a convex miss-ratio curve that scan-heavy workloads violate ([S3-FIFO](https://dl.acm.org/doi/10.1145/3600006.3613147)). It also recovers slowly. After a scan drives p toward 0, T1 regrows in steps of about 1. When churn follows the scan, "ARC continues to evict from T1 and behaves similar to LRU" while B2 stays empty. And because T2 is an LRU list, ARC "is unable to capture the full frequency distribution" and thrashes on churn ([CACHEUS](https://www.usenix.org/system/files/fast21-rodriguez.pdf)). ARC can exhibit Belady's anomaly, where miss ratio rises with cache size on some workloads; SIEVE reports this from earlier work that the notes did not trace ([SIEVE](https://www.usenix.org/system/files/nsdi24-zhang-yazhuo.pdf)). Finally, its LRU hit path serializes on a global lock, which is why CAR exists ([CAR](https://www.usenix.org/legacy/publications/library/proceedings/fast04/tech/full_papers/bansal/bansal.pdf)). That last point is irrelevant in a single-threaded Python simulator. The first four are precisely the gaps a per-object reuse predictor can close: separating new-but-popular keys from one-hit wonders inside T1, and carrying real frequency information inside T2.

## On the project's own traces, the candidate generator caps the ceiling

A smoke test run while preparing this plan asks the question that decides the architecture before any model is trained. If the scorer were *perfect*, how high could each design go? The test replayed both 100k-request project traces with scratch implementations of LRU, SIEVE, S3-FIFO and ARC, and with Belady's MIN computed from the traces' own next-use times. It also ran three "oracle" designs, each choosing, among K = 4 candidates, the one whose true next request is farthest away. The first oracle picks from the LRU tail, which is the current architecture's shape. The second picks from the tail of the list that ARC's REPLACE selects. The third picks from the tail of the main region behind a 10% probationary FIFO, the design the previous plan recommended. The capacities were 30 and 300 objects: 0.16% and 1.6% of zipf_100k's 18,486 keys, and 0.6% and 6% of web_traffic_100k's 4,992 keys.

| SIEVE | 54.00 | 69.94 | 8.40 | 59.07 |
| S3-FIFO | 53.63 | 70.51 | 9.02 | 68.46 |
| ARC | 52.83 | 70.55 | 8.43 | 68.87 |

| Oracle over 4 main-tail candidates behind probationary FIFO | 53.67 | 70.49 | 10.71 | 68.73 |

Three conclusions follow, and all of them come with caveats. First, **the current LRU-tail design cannot beat ARC even with a perfect model** in three of four settings. On zipf at c=300 the oracle closes only 14% of the LRU-to-Belady gap, while ARC closes 65%. The LRU tail offers only recency-cold keys, and a frequency-dominated trace needs the model to see frequent keys too. Second, the ARC-shell oracle beats every heuristic in every setting. Its margin over ARC is +2.3, +0.7, +8.1 and +1.3 points, closing 81%, 72%, 43% and 81% of the LRU-to-Belady gap. Third, the probationary-FIFO shell's ceiling sits below the ARC shell's everywhere. In that shell the model never sees probationary evictions, whereas inside ARC it can rescue a new-but-popular key from the T1 tail, which is ARC's documented blind spot. ARC and S3-FIFO are within about a point of each other on these traces, unlike the web/KV literature, where S3-FIFO usually leads. ARC's p on zipf at c=30 settled near 1, meaning T1 had collapsed to about one slot, just as the literature describes for small caches.

These numbers are an **inference aid, not a result**. There are two synthetic traces, one run each, the implementations are quick scratch versions not yet validated against libCacheSim, and the scorer is an oracle. A learned model realizes only part of any oracle ceiling, and the literature contains no measurement of how large that part is inside ARC. Phase 0 must repeat this exact test on real traces through libCacheSim before the shell choice is final.

## Policy-level control and per-object scoring answer different questions

The user's "policy type base" framing names a real fork in the design space. **Policy-level control** learns a few numbers about the *cache*: ARC's p, S3-FIFO's queue ratios, or weights over expert heuristics. The action space is tiny, the signal is aggregate (ghost hits, windowed hit rate), and the worst case stays close to the underlying heuristic. **Per-object scoring** learns about *keys*: which resident item returns last. It has a higher ceiling, because only it can approach Belady within a list, but it costs per-eviction inference and can fail badly. LAH attributes that failure to "objective mismatch, where improvements in prediction metrics do not translate into fewer misses", and measures LRB's worst-case regression at 20–72% against 0.8% for its cache-level learner ([arXiv:2608.27975](https://arxiv.org/html/2608.27975), preprint). ARC is pure policy-level learning with a hand-written update rule. LeCaR and CACHEUS replace that rule with regret minimization over two experts, using history lists that behave exactly like ARC's ghosts ([LeCaR](https://www.usenix.org/system/files/conference/hotstorage18/hotstorage18-paper-vietri.pdf); [CACHEUS](https://www.usenix.org/system/files/fast21-rodriguez.pdf)). LAH learns S3-FIFO's parameters with a GBDT from 73 cache-level features. It argues that "choosing the right parameter is much more important than per-miss adaptivity", and it names ARC's recency/frequency balance as a parameter the same approach could learn, but it only builds the S3-FIFO version ([arXiv:2608.27975](https://arxiv.org/html/2608.27975)). The two levels compose rather than compete. In the recommended shell, ARC's policy-level p picks *which list* loses a slot, and the per-object model picks *which key* within it. The hybrid inherits ARC's structural prior and floor, while spending model capacity where the smoke test shows headroom.

The research notes searched for "learned ARC", "RL-ARC", "DeepARC" and RL control of ARC's T1/T2 target and **found no such paper, peer-reviewed or preprint**. The only "ARC-RL" hit was an unrelated robotics paper ([arXiv:2605.19503](https://arxiv.org/abs/2605.19503)). Every ARC-specific integration below is therefore graded by how much neighbouring evidence supports it.

## RLCR transfers as a loss, and ModernBERT does not belong on the hot path

The user asked specifically about reinforcement learning for calibrated decisions and about modern encoders. Each has a real but narrow place, and ARC sharpens where RL can legitimately enter.

| Idea | Verdict | Where it fits | Where it does not |
|---|---|---|---|
| **RLCR** (RL with a Brier-augmented reward) | Adopt the *insight*, not the RL | Train the scorer's P(reuse within H) head directly with Brier or log loss. Use the calibrated probabilities for abstention to ARC's LRU victim, for admission, and for cost-aware eviction | An RL training loop for per-object eviction: labels are action-independent, so RL adds variance with no benefit |
| **Classic RL / bandits** | Retire from the per-object scorer; allow at the policy level | A bandit or Hedge controller over ARC's p band or S3-FIFO's parameters (Option D), where the action changes future cache state | Per-eviction value learning on an LRU trajectory (the current design) |
| **ModernBERT** (149M/395M) | Not on the hot path | Offline teacher, or a once-per-key embedding at insert time, *only if* keys are text (URLs, paths, SQL) | Per-eviction scoring of integer keys: no transferable prior, and 3–5 orders of magnitude over budget |
| **mmBERT** (140M/307M) | Weaker fit than ModernBERT | Only if keys are multilingual text, such as search queries in many languages | Anything with integer keys. About two-thirds of its weights are a 256k-token vocabulary table |
| **Other encoders** (Ettin-17M, NeoBERT, EuroBERT) | Ettin-17M is the most defensible pretrained option, if one is needed at all | Frozen feature extractor for string keys, validated by ablation first | Fine-tuning with LoRA for integer traces |
| **Small transformer trained from scratch** | Best "modern sequence model" option | Offline Parrot-style teacher over the last 32–80 accesses, distilled into the fast student | Online per-eviction inference in Python |

**RLCR** shows that rewarding a model with a bounded proper scoring rule, correctness plus a Brier term on its stated confidence, yields predictions that are both accurate and calibrated, whereas ordinary RL degrades calibration ([Damani et al., arXiv:2507.16806](https://arxiv.org/abs/2507.16806), a preprint). The transfer to eviction is simpler than the name suggests. Whatever the cache did, the outcome "was key *i* requested again within H requests?" becomes observable for every candidate after a delay. The team can therefore minimize the Brier score (p̂ − y)² or log loss *directly* by SGD, which is the objective RLCR's reward induces, without the variance of policy gradients. RL-with-Brier would be needed only if the label depended on the action, and for per-object labels in a trace-driven cache it does not. ARC's p is different. The hit rate that follows a p setting *does* depend on past p choices, so controlling p is a genuine sequential decision. That makes it the one place in this project where an RL-style controller is well posed. Even there, the published successes are regret minimizers and GBDT classifiers, not deep RL ([CACHEUS](https://www.usenix.org/system/files/fast21-rodriguez.pdf); [arXiv:2608.27975](https://arxiv.org/html/2608.27975)). A cheaper evaluator also exists in a simulator (our inference). Because ARC with p frozen is FRC_p, a handful of key-only FRC_p shadows on a grid of p values give exact counterfactual hit rates for each setting, with no reward-model variance.

Calibration still earns its keep in the per-object model. With unit miss cost, evicting argmin p̂ is invariant to any monotone recalibration, so calibration adds nothing to raw ranking. It matters for three decisions the plan relies on: when to *abstain* to ARC's own victim, when to *refuse admission* (p̂ < τ), and how to trade reuse probability against size or fetch cost (evict argmin p̂ᵢ·costᵢ). Shen, Vitercik and Wikum make the general case that calibrated predictions outperform a single global trust parameter and conformal intervals as the interface between ML and online algorithms, though their case studies are ski rental and scheduling, not caching ([ICML 2025](https://proceedings.mlr.press/v267/shen25f.html)). The research notes found **no paper that applies RLCR or conformal prediction to cache eviction**, so this transfer is an inference. The honest pitch is "trained with a proper-scoring-rule objective following RLCR's calibration result, with expected-cost decisions and abstention to ARC". Calling it RL would overclaim.

**ModernBERT** is a 22-layer, 8,192-token English text-and-code encoder in 149M and 395M sizes, built for fast inference on *GPUs* such as the T4 and RTX 4090 ([Warner et al., arXiv:2412.13663](https://arxiv.org/abs/2412.13663); [Hugging Face blog](https://huggingface.co/blog/modernbert)). **mmBERT** applies the same architecture to 1,800+ languages in 140M and 307M sizes. Its 256k-token Gemma 2 vocabulary accounts for roughly 197M of mmBERT-base's 307M parameters ([model card](https://huggingface.co/jhu-clsp/mmBERT-base); [Marone et al., arXiv:2509.06888](https://arxiv.org/abs/2509.06888)). Both papers are preprints. The project's keys are integers: `item_id` in every CSV. A text tokenizer splits "4812337" into arbitrary digit pieces, and neither English nor multilingual pretraining carries causal information about when opaque IDs recur. Parrot, the strongest attention-based replacement policy, learns key embeddings from scratch or with a byte-level embedder and uses no pretrained language model ([Parrot §4.5](https://arxiv.org/abs/2006.16239)). The notes found **no published use of ModernBERT, mmBERT, NeoBERT, Ettin or EuroBERT for cache replacement or prefetching**.

Cost settles the question. The available CPU figures are weak: BERT-tiny at roughly 10–20 ms per unbatched inference ([HF community blog](https://huggingface.co/blog/tlogandesigns/using-ml-to-flag-fair-housing-violations)), and an unverified report of about 108 ms for a ModernBERT-based model on a laptop CPU ([tech-insider.org](https://tech-insider.org/supersonic-labs-julia-1-cpu-decision-model-2026/)). Against LRB's 30 µs and HALP's 720 ns per comparison, that is three to five orders of magnitude too slow. At 10 ms per decision, one million evictions take about 2.8 hours of replay. If the project later caches *string* keys, the defensible pattern is to embed each key once at insert time with a small frozen encoder. Ettin-encoder-17M is the smallest ModernBERT-style checkpoint ([Weller et al., arXiv:2507.11412](https://arxiv.org/abs/2507.11412)). Compress the embedding to a cluster ID or a few PCA dimensions, feed it to the student as a feature, and adopt it only if an ablation shows it adds signal. The "modern sequence model" story that holds up is teacher–student. Glider trained an attention-LSTM offline, found that an unordered set of recent PCs sufficed, and deployed a tiny integer SVM "with orders of magnitude lower cost" ([Shi et al., MICRO 2019](https://www.cs.utexas.edu/~lin/papers/micro19c.pdf)). DART distilled an attention prefetcher into table lookups with **99.99% fewer operations and a 170× speedup** for an F1 drop of 0.09 ([Zhang et al., arXiv:2401.06362](https://arxiv.org/abs/2401.06362), a preprint). Parrot's own authors warn that "model latency may overshadow gains" ([Parrot §7](https://arxiv.org/abs/2006.16239)).

## Option B inside an ARC shell wins, with the FIFO shell as runner-up

Five options span the realistic design space. They are cumulative rather than exclusive. B is built on A's offline pipeline, C adds a teacher on top of either B variant, and D is an independent policy-level track.

**Option A: minimal Belady-imitation upgrade.** Replace the DQN with a frozen supervised student. At every eviction, log features for the candidates, label each with its true next-use distance from the trace, and train either a LightGBM regressor on log(1 + time to next request) with L2 loss (the LRB/3L-Cache choice) or a one-hidden-layer MLP with a ranking loss. Run 2–3 DAgger rounds, then evict the candidate with the largest predicted reuse distance. Candidates come from whichever shell Phase 0 selects.

**Option B-ARC (recommended): online calibrated learner inside ARC.** The data plane is the ARC class above, with one change to `_replace`. After REPLACE picks the list, the model scores the K = 4 entries at that list's LRU end and names a victim, or abstains, in which case ARC's own LRU victim goes. The victim enters B1 or B2 as usual, so p keeps adapting. The model learns live from delayed labels. Candidate features are snapshotted into a pending buffer at each eviction, evicted keys keep a metadata record in a bounded ghost table that is separate from and longer than B1/B2, and labels resolve when the key returns or when horizon H expires. Minibatch SGD runs every 1,024 resolved labels, following HALP. The model has two heads: a calibrated P(reuse ≤ H), trained with Brier or log loss, and an auxiliary log-reuse-distance head. A 3–5-member ensemble supplies uncertainty for abstention. A key-only **shadow ARC** runs on the same stream. When the model's windowed misses exceed the shadow's by a margin, every decision abstains, which makes the cache pure ARC until the model recovers. This is Chledowski et al.'s "switch whenever one becomes worse" combiner, which they found to be "cheap worst-case insurance" ([arXiv:2106.14693](https://arxiv.org/abs/2106.14693)). It matches Wei's result that following a predictor combined with a robust policy is the best a deterministic algorithm can do ([arXiv:2005.13716](https://arxiv.org/pdf/2005.13716)). ADWIN detectors watch the miss gap to the shadow and the shadow's p/c. On an alarm they force fallback, boost the learning rate, and discard labels created before the change. The design has two timescales. ARC's p reacts within roughly c misses at zero training cost, while the model catches up after about H plus one update interval (an inference, to be measured).

```python
# B-ARC: ARC chooses the list, the model chooses the victim (sketch).
def _replace(s, x_in_B2):
    use_T1 = s.T1 and (len(s.T1) > s.p or (x_in_B2 and len(s.T1) == s.p))
    L, B = (s.T1, s.B1) if use_T1 else (s.T2, s.B2)
    tail = list(islice(L, 4))                        # HALP's K
    v = None if s.fallback else s.scorer.pick(tail, in_T1=use_T1)  # None = abstain
    v = v if v in L else tail[0]                     # abstain -> ARC's own LRU victim
    del L[v]; B[v] = None
    s.pending.snapshot(tail, victim=v, t=s.t)        # delayed labels for all 4
```

**Option B-FIFO (runner-up): online calibrated learner behind a probationary FIFO.** This is the previous plan's shell. A 10% S3-FIFO-style probationary FIFO evicts one-hit wonders without calling the model, and the model scores the tail of an LRU main region. Everything else is identical to B-ARC, with a shadow of the model-off shell as the fallback. It calls the model less often, which is good for latency. The local oracle test, however, puts its ceiling below B-ARC's everywhere, because it gives the model no say over newcomers. It wins only if Phase 0 on real traces shows S3-FIFO clearly ahead of ARC *and* its oracle ceiling ahead of B-ARC's.

**Option C: transformer teacher distilled into a fast student.** Train a small from-scratch transformer (1–2 layers, 32–64 dimensions) over the last 32–80 accesses with Parrot's ranking loss plus the reuse-distance auxiliary head. Distill its candidate scores into the B student, following Glider and DART. ModernBERT enters only here, and only for string keys.

**Option D: policy-level learning only.** Keep a pure heuristic data plane and learn its parameters from cache-level features. The paper-backed form is LAH on S3-FIFO: a GBDT picks among 18 validated configurations, needs about 73 KB of state and under 2 ms of asynchronous inference, and stores no per-object metadata ([arXiv:2608.27975](https://arxiv.org/html/2608.27975)). The novel form, a learned-ARC, has a slow controller that clamps p to a learned band or picks a per-regime step size. It uses ARC-native features: hit positions within T1/T2, the B1/B2 ghost-hit rates, and the one-hit ratio. A Hedge or bandit controller over a grid of FRC_p shadows is the defensible "RL for calibrated decisions" version. This form is unpublished and must be treated as a research bet.

| | A: Offline imitation | **B-ARC: online learner in ARC** | B-FIFO: online learner behind probationary FIFO | C: Transformer teacher → student | D: Policy-level (LAH / learned p) |
|---|---|---|---|---|---|
| **Expected hit-rate gain** | LRB/3L-Cache class on stationary traces: mean single-digit % miss reduction versus LRU across real traces ([3L-Cache](https://www.usenix.org/system/files/fast25-zhou-wenbin.pdf)); must beat ARC and S3-FIFO | Local oracle ceiling is +0.7 to +8.1 points over ARC; the learned share is unmeasured. Floor ≈ ARC. Recovers after shifts | Local oracle ceiling is below B-ARC's in all 4 settings. Floor ≈ S3-FIFO-like shell | Teacher has Parrot-level headroom; the student keeps an unmeasured part of it | LAH: +26% efficiency over S3-FIFO, best worst case (preprint). Learned-ARC: unknown |
| **Decision latency** | ~10–30 µs per eviction with a compiled GBM ([lleaves](https://github.com/siboehm/lleaves); [LRB](https://www.usenix.org/system/files/nsdi20-paper-song.pdf)) | Same as A, on every eviction; ARC bookkeeping is O(1) | Same as A, but probationary evictions skip the model | Teacher is offline only; student as B | Heuristic speed; controller runs asynchronously |
| **Effort (hackathon days)** | 2–3 | +3–5 on top of A (ARC class is ~30 lines) | +3–5 on top of A | +5–10 on top of A | 2–4 for LAH-style; learned-ARC is open research |
| **Risk** | Low. Frozen model degrades under drift; no safety net | Medium. Label plumbing and fallback thresholds. The ARC shell rests on inference; the S3-FIFO literature favours the FIFO structure on web/KV traces | Medium. Lower ceiling | High. Distillation gap, training cost, little evidence for key-value traces | Low for LAH-style; medium for learned-ARC (no paper) |
| **ARC's role** | Baseline; candidate source if chosen | Shell, candidate generator, fallback, drift signal, baseline | Baseline and optional shadow | Via B | Controlled object (learned-ARC) or baseline |
| **Improves live?** | No | Yes, on two timescales | Yes | Only through B | Partly: periodic re-prediction |

**The recommendation is B-ARC, built in the order A → B, with C and D as stretch tracks.** ARC's adoption is exact. It is the baseline every result is reported against. Its REPLACE rule chooses the list, and its list tails supply the four candidates. Pure ARC is the abstention action and the fallback. A key-only ARC shadow is the comparator for the switch and the champion/challenger gate. The shadow's p/c feeds a secondary drift detector. ARC does *not* replace the pending-label ghost table, does not set the label horizon, and does not become an expert in a mixer, since CACHEUS and LeCaR both found ARC a poor expert. The decisive gate sits in Phase 0. If, on the real trace suite, the ARC-shell oracle ceiling does not exceed both S3-FIFO and the FIFO-shell ceiling on most traces, switch to B-FIFO without further debate. Model work is identical in both shells, so the switch costs about a day.

## The training pipeline runs from oracle labels to live updates

**Traces and labels.** Start with the traces on disk: `zipf_100k.csv`, `web_traffic_100k.csv`, and the archived bursty, adversarial, periodic and Zipf-α generators, which are ready-made drift tests. Add one ARC-specific stress trace: a long scan, then churn, then an LRU-friendly phase. That pattern pins p near 0 and exposes ARC's slow recovery ([CACHEUS](https://www.usenix.org/system/files/fast21-rodriguez.pdf)). Then add 5–20 real traces through libCacheSim. Its Python package offers a `SyntheticReader`, a `TraceReader` for the oracleGeneral format (which stores `next_access_vtime` for Belady), and a `PluginCache` whose hooks can call the model ([libCacheSim-python](https://github.com/cacheMon/libCacheSim-python); [libCacheSim README](https://github.com/1a1a11a/libCacheSim)). Traces come from the cacheMon dataset repository ([cache_dataset](https://github.com/cacheMon/cache_dataset)). Lengthen synthetic runs to 1–10M requests: Parrot trained on about 5M accesses per program ([Parrot §5.1](https://arxiv.org/abs/2006.16239)), and the current 18k-row training set is far too small. Labels come from a single reverse pass per trace. The primary regression target is log(1 + time to next request), capped at twice the memory window for keys never seen again, following LRB. LRB found log-scale L2 regression beat seven other LightGBM objectives and the binary alternatives ([LRB §4.2–4.3](https://www.usenix.org/system/files/nsdi20-paper-song.pdf)). The calibrated head's binary label is y = 1 if the key is reused within H requests. Set H from the **relaxed-Belady boundary**: run Belady on a training prefix and take the minimum time to next request among the objects MIN evicts. Relaxed Belady costs only 9–13% more misses than MIN, against a 25–40% gap between the best heuristics and MIN ([LRB §3](https://www.usenix.org/system/files/nsdi20-paper-song.pdf)). ARC's ghost horizon of about c evictions is typically shorter, which is why the plan keeps its own ghost table. Sample training examples over *objects*, not requests, to avoid popularity bias. The same boundary gives LRB's **good decision ratio**, the fraction of evictions whose victim's next request lies beyond the boundary. It is a fast offline proxy that "correlates strongly with byte miss ratio".

**Features.** Replace the three unnormalized features with about 8–12 cheap, incrementally maintained ones. These are age (time since last access), the last 3–8 inter-arrival deltas (with missing values marked explicitly), 4–10 exponentially decayed counters, frequency within a sliding window, and size and cost if objects ever vary. All go through log1p for the MLP. LRB's decayed counter updates as Cᵢ = 1 + Cᵢ·2^(−Δ₁/2^(9+i)) at each access ([LRB §4.3.1](https://www.usenix.org/system/files/nsdi20-paper-song.pdf)). The exponent was reconstructed from a garbled PDF extraction and should be checked against the paper. 3L-Cache shows that six features suffice for a GBM ([§4.2](https://www.usenix.org/system/files/fast25-zhou-wenbin.pdf)). In B-ARC, add an in-T1 flag, because the model only ever compares keys within one list. Keep the feature store's per-key history **longer than ARC's 2c directory**. The model's advantage in T1 comes from remembering that a "new" key was popular before ARC forgot it (an inference consistent with the oracle test). p/c and the B1/B2 hit mix enter only through an ablation. Drop the all-time frequency dict and the rank feature. Hashed-key embeddings are worth trying only if key IDs have structure ([Parrot §4.5](https://arxiv.org/abs/2006.16239)).

**Losses.** Combine three signals, each backed by a specific result. The *ranking* loss orders the candidates within one eviction event by true reuse distance. Parrot's differentiable NDCG ranking beat plain log-likelihood by 3.5% ([Parrot §5.3](https://arxiv.org/abs/2006.16239)), and HALP's pairwise binary cross-entropy on "who returns first" is the cheap online version ([HALP PDF](https://www.usenix.org/system/files/nsdi23-song-zhenyu.pdf)). The *reuse-distance* regression head (MSE on log distance) is the one to keep even if nothing else is: removing it cost Parrot 16.8% normalized hit rate. Parrot also found that evicting directly on the predicted distance was worse than using it as an auxiliary loss, because small log errors flip close decisions. The *calibration* head uses Brier or log loss on P(reuse ≤ H), both strictly proper, following RLCR. With LightGBM, the equivalent options are L2 regression on the log target or a `lambdarank` objective grouped by eviction event; no study compares the two for eviction, so run both.

**DAgger.** Round 0 collects states by following Belady, or ARC as a cheaper and closer stand-in for the shell. Each later round replays the trace *with the current learned policy driving evictions inside the shell*, logs every candidate set it faces, relabels those candidates with true next-use distances, aggregates, and retrains. Parrot re-collected data every 5,000 updates, and on-policy training helped on average but not on every program ([Parrot §5.3](https://arxiv.org/abs/2006.16239)). Two or three rounds are enough for the hackathon. DAgger matters more in B-ARC than in an LRU shell, because the model's victims feed B1/B2 and so shift p. The states the learned policy visits therefore differ from pure ARC's.

**Online fine-tuning.** Live learning is the same labelling done with a delay. At each eviction, every candidate's features go into a pending dict keyed by object and timestamped. An evicted key keeps a small metadata record in an LRU-bounded ghost table, sized as a multiple of the cache as HALP does, so its label can still resolve ([HALP PDF](https://www.usenix.org/system/files/nsdi23-song-zhenyu.pdf)). A label resolves as y = 1 with the observed distance when the key returns, or as y = 0 once H requests pass. Three update cadences have been validated. HALP runs an MLP minibatch every 1,024 labels, and even per-example updates changed P95 byte miss by under 0.2%. LRB retrains a GBM from scratch on every 128K labels in about 300 ms. 3L-Cache retrains every 32K–64K. For an MLP in NumPy or PyTorch, the HALP cadence fits naturally; for LightGBM, periodic retrain-and-swap on a sliding window does. Until enough labels exist, abstain on every decision, which makes the cache run as pure ARC. That mirrors LRB's LRU cold start ([LRB §4](https://www.usenix.org/system/files/nsdi20-paper-song.pdf)).

```python
# B-ARC online loop (per request t, key k). The hit path touches no model.
if k in pending:                                  # delayed label resolves
    x, t0 = pending.pop(k)
    buf.append((x, 1.0 if t - t0 <= H else 0.0, log1p(t - t0)))
expire_pending_older_than(t - H, label=0.0, into=buf)
if len(buf) >= 1024:                              # HALP cadence
    sgd_step(model, buf, loss=brier + aux_mse + pairwise_bce)
    buf.clear(); refit_temperature(recent_labels)
shadow_hit = shadow_arc.access(k)                 # key-only pure ARC
gap.update(ml_miss - (not shadow_hit))            # river ADWIN on miss gap
regime.update(shadow_arc.p / c)                   # secondary ADWIN on p/c
if gap.drift_detected or regime.drift_detected:
    cache.fallback = True; boost_lr(); drop_labels_before(t)
cache.fallback = cache.fallback and not recovered(window)  # hysteresis
```

**Calibration and abstention.** After each update, refit a single temperature (a 1-D search on log loss, [Guo et al., ICML 2017](https://arxiv.org/abs/1706.04599)) or an isotonic map on the last N resolved labels. Report a reliability diagram, expected calibration error and Brier score on resolved labels as first-class metrics. For uncertainty, stack 3–5 small MLPs initialized from different seeds or trained on bootstrapped minibatches ([Lakshminarayanan et al., NeurIPS 2017](https://arxiv.org/abs/1612.01474)). In NumPy that is one wider matrix multiply. Abstain to ARC's LRU victim when the ensemble's standard deviation exceeds τ, or when the calibrated margin between the model's pick and ARC's victim lies inside the ensemble noise. Tune τ on recent resolved decisions, or adapt it online with adaptive conformal inference, α ← α + γ(α − err), which keeps long-run coverage under arbitrary drift ([Gibbs & Candès, NeurIPS 2021](https://arxiv.org/abs/2106.00170)).

**Drift detection and safe promotion.** Feed `river.drift.ADWIN` the per-request difference between the learned cache's miss and the shadow ARC's miss. Add a detector on the Brier loss of resolved predictions, which catches calibration decay before it becomes hit-rate decay ([river ADWIN](https://riverml.xyz/dev/api/drift/ADWIN/)). Add the unpublished p/c detector as a third, cheap signal, and evaluate it on the drift traces before trusting it. After a regime shift, ghost-resolved labels describe the *old* regime for up to one horizon, so discard or down-weight labels created before an alarm. For model upgrades, run the challenger in its own key-only B-ARC shadow and promote it only when its windowed hit rate beats the incumbent's by more than 2σ under a paired block bootstrap. Because evictions do not change the request stream, this is *exact* off-policy evaluation with no importance weighting, and SHARDS-style spatially sampled miniature caches make such shadows cheap at scale ([Waldspurger et al., ATC 2017](https://www.usenix.org/conference/atc17/technical-sessions/presentation/waldspurger)). For a stronger theoretical guarantee than switch-on-worse, the Guard framework reaches (2H_{k−1}+2)-robustness while preserving 1-consistency at O(1) per-request overhead. It wraps LRB and Parrot through phase-based marking, independent of which shell is used ([Chen et al., NeurIPS 2025](https://arxiv.org/abs/2507.16242)).

**Evaluation protocol and baselines.** Split each trace by time: tune on the first 20%, as LRB does, or use Parrot's 80/10/10 split. Never split randomly. Also train on some traces and test on others. Sweep cache sizes at 0.1%, 1% and 10% of each trace's footprint; ARC's small-cache collapse makes the 0.1% point especially informative. Report five things per trace. The first is the miss-ratio reduction versus LRU, (mr_LRU − mr)/mr_LRU, plus the reduction versus ARC. The second is Parrot's *normalized hit rate*, (r − r_LRU)/(r_Belady − r_LRU). The third is the fraction of traces on which each policy is best. The fourth is the worst-case regression versus LRU, FIFO and ARC. The fifth is throughput and decision latency. Baselines are LRU, FIFO, ARC, SIEVE, S3-FIFO, W-TinyLFU, LeCaR, CACHEUS, LRB, 3L-Cache and Belady; add ARC-SIEVE if easy, and LHD and GDSF only if sizes vary. libCacheSim implements ARC, CAR, 2Q, LIRS, LeCaR, CACHEUS, S3-FIFO, SIEVE, W-TinyLFU, LRB, 3L-Cache and Belady, and replays over 20M requests per second, although LRB and GL-Cache need build flags ([libCacheSim README](https://github.com/1a1a11a/libCacheSim)). The notes did not confirm that the Python package exposes an `ARC` class. Cross-check the team's ARC class against libCacheSim's native ARC at unit object sizes, just as the team's LRU is checked. Use the Python plugin path for correctness checks, not speed numbers.

## Latency drops by scoring four candidates in one native call

Every deployed learned cache stays fast the same three ways. It calls the model only on evictions, over a small candidate set. It uses a tiny model. It runs that model in compiled code. The published numbers set the targets.

From those anchors the plan sets four team targets for the Python simulator. They are goals, not literature results. First, **p99 decision latency at or under 30 µs per eviction**, which is LRB's budget met with a sixteenth of LRB's candidates; the stretch goal is under 10 µs. Second, **end-to-end requests per second at least 50% of the same harness's Python ARC**, which is tighter than 3L-Cache's 3.4–6.4× CPU band. Third, **online training kept under 10% of total runtime**, against HALP's production 1.8%. Fourth, **zero model calls on the hit path**. ARC's hit path is two OrderedDict operations.

The route is ordered by effort. Start by profiling with `InstrumentedRLHybridCache` to confirm where the time goes. Cut candidates from 16 to 4, since HALP measured little gain beyond 4. The local oracle test agrees: inside ARC, going from 4 to 16 candidates added only 1.5 points on zipf at c=30 and 0.9 at c=300. Maintain features incrementally on access, as LRB does, with shifting deltas and decaying counters from a precomputed table. Then make each eviction **one native call**, either a Numba `@njit` forward pass over the 4×F candidate matrix or an lleaves-compiled GBM. Rust through PyO3, or a C plugin inside libCacheSim, is the last resort if Python still dominates. The shadow ARC roughly doubles shadow bookkeeping compared with a shadow LRU (four lists instead of one), still O(1). If latency is tight, one untested knob remains: score only T2 evictions and let T1 evict its LRU tail, measuring the ceiling cost with the oracle harness first. Two tempting moves do not pay off. Asynchronous or batched inference helps only in a multi-threaded server, not a single-threaded simulator. And int8 quantization of a roughly 10K-parameter model will not help much, because such models are dispatch-bound. That last point is unverified but consistent with the numbers above.

The phases gate each other on evidence. If Phase 0 on real traces shows the ARC-shell ceiling below S3-FIFO or below the FIFO shell, build B-FIFO instead; the model code does not change. If Phase 1 cannot beat ARC and match S3-FIFO, the answer is not a bigger model. It is Option D, learning the heuristic's parameters, which posts the best reported worst case. That is the clearest lesson of the 2023–2026 results.

## Conclusion

ARC's real contribution to this plan is not its hit rate, which modern FIFO heuristics match. It contributes a *structure* that tells a learned scorer where to look. The current project's deepest flaw turns out to be where its model looks, not how it learns. Scoring the LRU tail caps even a perfect predictor below a thirty-line heuristic on the team's own traces. Letting ARC choose the list gives the model newcomers and veterans to compare. It also turns "fall back safely" into "switch the model off", and pairs a fast policy-level learner (p) with a slow per-object one. That two-timescale split is the most useful way to read "policy type base". Policy-level adaptation reacts in about c misses at no training cost. Per-object learning closes the within-list gap that policy-level control cannot reach, and needs a horizon of labels before it catches up after a shift.

The honest caveat is that the ARC shell rests on neighbouring evidence (HALP's heuristic-agnostic candidates, ARC-SIEVE's within-list gains, robust-caching theory's fallback-agnostic combiners) and on an oracle smoke test over two synthetic traces. No one has published a learned ARC. That makes Phase 0's oracle-ceiling harness the highest-value day of the project: it decides the architecture with no model trained. If B-ARC survives Phase 0 and Phase 2, the team has a novel, defensible result. If it does not, the same pipeline drops into the FIFO shell or into LAH-style parameter learning with no wasted model work. Four load-bearing claims remain open: LAH's venue and metric definitions, RLCR's transfer to eviction, ModernBERT's CPU latency, and ARC's 4N competitive bound, all preprint-level or unverified.
